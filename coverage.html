UBL 2.5 element coverage

UBL 2.5 element coverage: initial analysis

How many UBL 2.5 elements appear in at least one sample document in xml/, which are missing, and where each missing element fits best: in one of the current examples, or in a new example document.

Generated tables with every missing element: element-coverage-details.md. Produced by tools/coverage.py (see Reproduce).

Method

  • Element = child in its context. Each BBIE and ASBIE of the UBL 2.5 model (mod/UBL-Entities-2.5.gc of os-UBL-2.5) counts as one element: Address/StreetName and Party/PostalAddress are separate elements, and so are Invoice/Note and Order/Note. That gives 5,443 elements: 2,570 at document level (101 document types) and 2,873 in the 310 library aggregates.

  • Counted: the cac/cbc elements in the 75 sample documents. UBL-Invoice-2.0-Detached-Signature.xml is an XML signature, not a UBL document. Not counted: attributes (schemeID, currencyID, …), code-list values, and extension content (signatures).

  • Placement (automatic, then reviewed below). Each aggregate has home documents: the document types that reach it in the fewest steps.

    • extend: a home-document example already contains the parent, so add the element there.
    • add structure: a home-document example exists, so add the parent (and the path to it) there.
    • new example: no home document has an example.

    If several examples qualify, the script picks the one that needs the fewest new elements, already uses the parent most fully, and is the newest version.

  • Validity baseline: all 75 examples are valid against the UBL 2.5 OS schemas (xsdrt/maindoc, checked with xmllint). Every element they use exists in the 2.5 model.

Review of the automatic placement

The script only uses the structure, so some placements are technically possible but not where the element belongs in meaning. My corrections:

Elements Automatic placement Better fit Why
Circularity, new in 2.5 (CircularityProfile, EndOfLifeTreatment, ResourceConsumption, WasteGenerated, repairability Score) Invoice line item Catalogue (new) Product master data that the supplier publishes, not billing data
Maritime port reporting (MaritimeHealthDeclaration, BallastWaterSummary, ISPSRequirements, MaritimeWaste, DestinationPortCall, Storage) Waybill-2.0 CommonTransportationReport-2.3 That is the ship-to-port reporting document these were added for (2.3); a waybill is a transport contract
Tendering terms and process (TenderingProcess, AwardingTerms, AwardingCriterion, TendererQualificationRequest, …) PriorInformationNotice ContractNotice / CallForTenders (new) A PIN announces a procurement; the full terms belong in the contract notice and call for tenders
ElectronicAddress, SecurityListing (party, new in 2.5) Waybill consignor; Invoice payee BusinessCard Party profile data; BusinessCard is the document that exchanges it
FuelConsumption, FuelMetering, FuelProperty (2.4) Invoice-2.1 delivery New Invoice variant (fuel delivery) Fits the Invoice, but as its own scenario rather than in the generic example
InsurancePolicy (shipment, new in 2.5) Waybill-2.0 Waybill or BillOfLading (new) Either works; BillOfLading if we add one
PenaltyInterestRate (new in 2.5) Invoice payment terms Invoice, and also Reminder Late-payment interest is what a reminder charges

General observations:

  1. Don't put everything in one example. Some aggregates have 50–90 missing elements. Adding them all to one existing file makes it unreadable. Scenario-specific variants (e.g. Invoice-2.5-Example-Fuel) are clearer and fit the "coherent world" of part 2.
  2. Many targets are old OASIS examples (Waybill-2.0, Statement-2.0, DespatchAdvice-2.0, ReceiptAdvice-2.0, RemittanceAdvice-2.0). They are valid against 2.5 but reflect the 2.0 data. Changing them changes files that were published by OASIS.
  3. Coverage of 2.5 is the weakest point: 386 of the 387 elements new in 2.5 are not in any example yet. That is also where examples help adopters most.

Open decision

Should coverage be added by changing the OASIS example files (the history of xml/ then continues after os-UBL-2.5), or by adding new example files next to them and leaving the OASIS originals as published? The second option keeps the reconstructed history clean, and the new files can follow the part 2 party set from the start.

Reproduce

The model file is in the release zip (https://docs.oasis-open.org/ubl/os-UBL-2.5/UBL-2.5.zip, mod/UBL-Entities-2.5.gc).

python3 tools/coverage.py --model /path/to/UBL-Entities-2.5.gc --examples xml > analysis/element-coverage-details.md
