Abstract:

This note describes how a coherent set of UBL example documents is created and maintained: a fictional world of organisations that exchange UBL documents with each other, and for every value in every example the reason why it fits the semantic meaning of its element in that context.

1 Introduction

1.1 Purpose

UBL defines hundreds of document types and thousands of elements. Its definitions say what an element means, but readers also need to see how an element is used: with which value, in which context, and in relation to the other documents in a business process.

This note describes a method for creating UBL example documents that show exactly that. The examples form one coherent set: they share the same organisations, products and timeline, and documents that belong together refer to each other the way they would in real exchanges.

1.2 Scope

The method covers:

  • the fictional world in which the examples take place;

  • how a value is chosen for an element, and how the reason for that choice is recorded;

  • how examples are checked, within a document and across documents;

  • how examples are reviewed and maintained over UBL versions.

The examples illustrate UBL. They do not define a profile, a customization or a national implementation, and a value used in an example is never the only valid value.

1.3 Starting point

The example set starts from the sample documents that OASIS published with each UBL 2.x release. Their history, from UBL 2.0 to UBL 2.5, is kept in the repository, one document per commit.

2 Principles

2.1 One fictional UBL world

All examples take place in the same fictional world: a set of organisations that do all their business with UBL. Documents that belong together, such as a catalogue, an order, a despatch advice and an invoice, or the transport and customs documents for the same goods, tell one consistent story.

2.2 Universal, not tied to one region

The world includes business within one country, within a region and between continents. No country, legal system or process is the default. Where an example uses a country-specific identifier or rule, it is one illustration among others, not the way UBL has to be used.

2.3 Every value has a reason

For each element in each example, the reason for its value is recorded: why the value fits the semantic meaning of the element, as defined by UBL, in the context of that document and that business situation. The reason refers to the UBL definition first. Country rules or a specific process only appear as illustrations.

2.4 Proven, not only plausible

Values are checked automatically:

  • the document is valid against the UBL schemas and code lists;

  • the document is consistent in itself, for example totals, dates and internal references;

  • the documents are consistent with each other, for example parties, references between documents and quantities along a process.

2.5 Open and reproducible

The world, the reasons, the checks and the history are kept in a public repository. Anyone can follow how an example was made, reproduce it, reuse it or challenge it.

3 The UBL example world

All examples take place in one fictional world. It is built in layers. Each layer adds one kind of data, is kept in its own file, and is checked before the next layer builds on it.

Layer File What it holds
Countries world/countries.json names, currencies, tax schemes, identifier and address schemes
Parties world/parties.json the organisations: place on the map, role, identity
Map world/map.json routes, towns and localities
Documents world/documents.json the flows of documents between the parties
Items world/items.json what the parties sell: goods and services, with prices
UBL model world/ubl-model.json extracted from the UBL 2.5 semantic model
Code lists world/codelists/ UBL default code lists with the world's codes added

3.1 Countries

The world has three countries: Urvania, Bayvarra and Lisavu, whose initials spell UBL. Two share a land border on the mainland; the third is an island overseas. They differ on purpose, so that the examples show how UBL carries different national arrangements in the same structure:

  • Urvania (XU) has a value added tax in the style of the EU VAT: charged at every stage, deducted by businesses, not charged on exports.

  • Bayvarra (XB) is a federal country whose states levy a retail sales tax, charged once, on the sale to the final consumer. Sales for resale, exports and sales to public bodies are exempt.

  • Lisavu (XL) has no general sales tax. Customs collects a customs duty and an import consumption tax when goods enter the island.

The tax schemes are identified with UN/EDIFACT 5153 codes: VAT, STT (state or provincial sales tax), CUD (customs duty) and IMP (import tax). Because 5153 has no code for a national sales tax, Bayvarra levies its sales tax at state level, which also gives the state in its addresses a purpose.

XU, XB and XL are ISO 3166-1 user-assigned codes, which exist for exactly this purpose; each follows the initial of its country's name. ISO 4217 has no such range for currencies. The world's currencies follow the ISO 4217 convention of the country code plus the initial of the currency's name: the ferra of Urvania (XUF), the lume of Bayvarra (XBL) and the coral of Lisavu (XLC). The convention limits the names: ISO 4217 already uses XUA and XBA to XBD, so Urvania's currency cannot start with an A and Bayvarra's not with A to D. Each code is checked against the current ISO 4217 list, so that none is a real code.

The three currencies also differ in their minor unit, because currencies do: the ferra has none (amounts are whole ferra, as with the Japanese yen), the lume has two decimals, and the coral three (as with the Bahraini or Kuwaiti dinar). An example that only ever shows two decimals hides a case that software must handle. Neither the countries nor the currencies are in the UBL default code lists. UBL lets trading partners use their own code lists in the second phase of validation, so the world has its own: copies of the UBL 2.5 default lists, unchanged, with the world's codes added and their own identification.

Each country also has its own payment practice, which every invoice of a seller there follows. Urvania gives 2 % discount for payment within ten days and charges statutory interest on late payment; Bayvarra charges a surcharge per month late and rounds cash payments to 5 cents, its smallest coin; the island gives 45 days. A transfer quotes a creditor reference in the structure of ISO 11649, made from the invoice number, so the payee can match it, and runs over the domestic clearing or, between the countries, the trade accord's payment link. Urvania also levies an energy tax per kilowatt hour, in two tiers, on which value added tax is then charged.

3.2 Parties

The parties are the organisations of the world, chosen so that every party role in every UBL document type can be filled (see the party cover analysis). Each party has:

  • a role, such as manufacturer, road carrier or contracting authority;

  • a place on the map, in a town or a locality;

  • an identity: a name, the identifiers of its country's schemes, a postal address in its country's format, an electronic address, a contact, and, where it is paid, an account at one of the world's banks.

Names are invented and checked against real organisations. E-mail addresses use the reserved domain .example (RFC 2606), so that none can reach a real organisation. Account numbers follow the structure of ISO 13616 with its check digits, using the world's country codes, but they are not called IBANs, because the world's countries are not registered IBAN countries.

3.3 Items

Every party that sells has items. Goods carry what the documents along their way need: a seller's item identifier, a world item number issued by the identifier issuing agency (twelve digits with a check digit, a scheme of the world, not a GTIN), a Harmonized System customs tariff code, the country of origin, dimensions, net and gross weight, and the packaging. Services have a unit and a price. Units of measure and packaging types are UN/ECE Recommendation 20 and 21 codes from the UBL default code lists. Prices are in the seller's currency. A unit price may be finer than the currency, as an electricity tariff of 27.3 ferra per kilowatt hour is, but every amount to pay is rounded to the currency's minor unit.

Items connect the chains. The park bench is made with slats from the sawmill and film from the packaging maker; the distributor resells the bench, and its own item points to the manufacturer's, so the maker's identifiers travel along. A component or a resold item is only possible if the maker or reseller orders it from that seller somewhere in the flows.

The maker's facts travel with the item wherever it appears: brand and model, properties with their test method and accepted range, certificates, the carbon footprint and the circularity profile. What belongs to one delivery is added only where the goods move: a despatch advice names the production lot, or the serial number of every casting, which stays the same when a cancelled despatch advice is replaced. A catalogue line adds the seller's terms (lead time, minimum and maximum quantity, the price list and its validity), and a till receipt during a promotion shows the discount on the shelf price.

3.4 Flows of documents

The parties do business in flows. Each country has its own raw material and industry: Urvania mines ore and makes park benches, recovering its production waste as recycled plastic; Bayvarra saws timber, makes furniture, packaging and clothing, and distributes and retails; the island Lisavu grows and gins cotton, its export. Goods cross the land border by road, rail and river barge and go overseas by sea and air in both directions; there is a public tender, a temporary export with an ATA carnet, and a utility in each country. Each flow starts from the business: who buys from whom, on which delivery terms, and therefore who arranges and pays the transport. A distributor that buys free carrier (FCA) books the truck itself and names the carrier in its order; a retailer that buys delivered duty paid (DDP) leaves the transport to its supplier, who then needs an outgoing waybill.

Every document in a flow records:

  • the document type, its sender and its receiver;

  • why it is sent, in business terms;

  • every party it mentions, at its place in the UBL structure, for example the road carrier at Order/Delivery/Despatch/CarrierParty.

A flow also lists its transport legs: the mode, from which party to which, and the carrier. The goods only move where the world allows it. A road leg needs a road from party to party, so a truck cannot drive to the island; a rail leg needs a rail line between them, a barge needs the river at both ends, a ship a sea route from port to port and an aircraft an air route from airport to airport. The carrier must have a vehicle, train, vessel or aircraft of that mode in its fleet, and every carrier a document of the flow names must carry one of its legs. Domestic jobs go to a carrier of that country: a truck of one country driving within another would be cabotage, which only happens where a document says so.

3.5 Who sends and who receives

Who sends and who receives a document type comes from the UBL 2.5 semantic model first: the elements SenderParty and ReceiverParty, or a definition of the document or of one of its party elements, such as "The Party who submits this Tender". Where the model does not say it, the party role table of the UBL specification is used. Where neither says it, the choice is marked as inferred, with the definitions it rests on. Every quote is checked word for word against its source.

4 Choosing and documenting values

Every value in an example document comes with the reason why it is that value. The reason is recorded where the value is made, and a document with a value without a reason is not built.

4.1 Where values come from

A value in an example comes from one of these sources, and its reason says which:

  • The world's layers. Party names, addresses, identifiers and accounts come from the identity of the party; items, their identifiers, customs tariff codes and prices from the items layer; currencies and tax rates from the countries layer. These values are the same in every document that uses them.

  • The structure of the flow. Which party sends the document, which receives it, and which other parties it names, at which place, come from the flow of documents, so the parties always sit where the business puts them.

  • The scenario of the flow. Document numbers, dates, quantities and the references between documents are what a flow adds; each carries its own reason, in business terms.

  • Code lists. Coded values come from the UBL default code lists or the world's own lists, and the reason names the list and the meaning of the code.

  • Calculation. Amounts are calculated from quantities and prices and rounded to the minor unit of the currency; the reason states the calculation. Every sum is stated in the document, as UBL requires, and never left to the receiver.

4.2 What a reason contains

A reason says why the value fits the element: what the element means in UBL, in this document, and what in the business situation makes this the value. It refers to the UBL definition and to the world's data first; a country rule or a specific process appears only as an illustration. For example, the quantity on an invoice for bulk ore is the weighed quantity from the despatch advice, not the ordered quantity, and its reason says so.

4.3 A party is described once per document

A party often plays several roles in one document: the buyer of an order is usually also its delivery party. Its full details (address, tax number, legal registration, contact, electronic address) are given once, at its first place in the document. Every later mention of the same party holds only its identifier and its name: enough to identify it, and never empty, as UBL requires (rule IND5). The same applies to a bank named more than once. The identifier is the party's number in its country's company register, given as PartyIdentification with the register as its scheme.

4.4 Only what UBL 2.5 endorses

The documents use only endorsed document types and elements, and they are validated against the schemas of the endorsed document types. Where UBL 2.5 replaced an element, the examples use the replacement: a party's electronic address, for instance, is carried in ElectronicAddress, because Party/EndpointID is deprecated.

4.5 Kept apart from the TC examples

The generated examples are kept in world/examples/, apart from the examples of the OASIS UBL Technical Committee in xml/, whose history is the base of this repository.

5 Checking the examples

The world is checked automatically every time the site is built. A build with a problem stops. The checks are layered like the world itself.

5.1 The world against the UBL 2.5 model

Every document in the world is checked against the UBL 2.5 semantic model:

  • every place where a party is mentioned exists in the structure of that document type;

  • the sender fills a sender element of the document and the receiver a receiver element, or the document says on whose behalf they act, as a customs broker does for an importer;

  • every mandatory party element at document level is filled;

  • every party of the world takes part in at least one document.

5.2 Only what UBL 2.5 endorses

The examples use only document types, associations and properties that UBL 2.5 endorses. Anything the model marks as deprecated is rejected. A transport service, for example, is invoiced with the Invoice, because the Freight Invoice is deprecated.

5.3 Nothing empty, nothing implied

Two rules of the UBL specification shape the data the world needs:

  • No empty elements (IND5). A UBL document never contains an element without content. Every party element must therefore hold at least one of its parts, even though none of them is mandatory in the schema. The identity of every party makes sure there is always something to put in it.

  • An absence carries no meaning (IND6). Leaving an element out never says anything; the sender states every value that matters, and every sum (section 2.2.2, "Manifest Values"). An order without a carrier does not say that the seller arranges the transport: its delivery terms must say so. The world therefore requires values that would otherwise be implied, such as the delivery terms of every order.

5.4 The parties

The identity of every party is checked: every party has a name and every organisation an identifier; tax numbers and account numbers carry valid check digits; the city in the address is the nearest town or locality of the party's own country and state; every account is held at a bank of the world in the same country; and a bank named in a document is the bank where that party keeps its account.

5.5 The items

Units and packaging types must be codes of the UBL default lists; world item numbers carry a valid check digit and are unique; prices are positive and in the seller's currency; gross weight is at least net weight. Every party that bills or offers in a document has items to put on its lines, and every party with items bills or offers them. The exchange rates between the currencies agree with each other.

5.6 The map and the code lists

The map is checked as a structure: one connected road network per landmass, houses on streets, nothing built on roads or water, believable terrain, and customs posts where roads cross a border. The world's code lists are checked to hold exactly the codes of the countries layer.

5.7 The example documents

Every example document is validated in the two phases UBL prescribes:

  • Phase 1: against the UBL 2.5 runtime schema of its document type, from the endorsed set.

  • Phase 2: its coded values against the code lists, using UBL's context/value associations (CVA). It runs twice. First UBL's own phase 2, unchanged, with the UBL default code lists: it must object to exactly the world's country and currency codes and to nothing else. Then the same associations with the world's code lists in place of the defaults: here every value, and the list identifier where a document gives one, must pass.

The committed examples must also be up to date: they are generated again from the world's layers and compared, so a change in the world cannot leave an example behind.

5.8 Still to come

Later layers add their own checks: document lines with items and quantities, amounts and taxes that add up, dates in a believable order, references between documents, and quantities that agree from order to invoice. These apply to the example documents as they are generated for every flow.
